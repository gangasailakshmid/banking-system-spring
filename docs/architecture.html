From customer registration to bank activation

Follow a customer ID from the Spring Boot dashboard through MySQL, MongoDB, PostgreSQL, and two Kafka topics.

Architecture

  • BrowserThe administrator signs in and uses the JSP registration wizard, customer directory, and edit form.
  • Spring BootSpring Security checks the session and protects form submissions with CSRF. Spring MVC routes saves to the registration coordinator. The Kafka publisher and listener run in this same process.
  • MySQL · 3306personal_details generates the shared customer ID. login_accounts stores administrator usernames and BCrypt password hashes separately.
  • MongoDB · 27017address_details stores each customer’s address and phone using the shared ID as _id.
  • PostgreSQL · 5432bank_details stores the bank information, status, and latest request UUID. bank_activation_outbox holds events awaiting publication.
  • Kafka · 9092The request topic triggers bank validation. The results topic carries the outcome. Both topics use the customer ID as the record key.

End-to-end registration flow

  1. Sign in and submit the registration

    The administrator completes the personal, contact, and bank steps. The controller validates the form and hands it to the registration coordinator.

    RegistrationController.java

  2. Write the three customer records

    MySQL saves the personal record and assigns the customer ID. The coordinator saves the MongoDB address under that ID, then invokes the bank activation service. PostgreSQL commits the bank row with IN_PROGRESS and its outbox request together.

    RegistrationRepository.java

  3. Publish the activation request

    The scheduled publisher reads the outbox, sends JSON to customer-bank-activation-requests, and removes the outbox row after Kafka acknowledges it.

    BankActivationMessaging.java

  4. Consume the request and validate the account

    The banking-system-activation group consumes the request. The service locks the PostgreSQL bank row and checks that the request UUID matches the pending attempt. It compares the saved account number with the prefix for the saved bank.

    BankActivationService.java

  5. Commit and publish the outcome

    PostgreSQL commits ACTIVATED or FAILED with a second outbox event. The publisher sends that event to customer-bank-activation-results. The grid’s Reload button reads the updated status from the app while preserving the current search and unsaved form entries.

Edits, retries, and transaction boundaries

Read, edit, and delete

The directory starts from MySQL and joins address and bank data by customer ID. Missing details remain visible and can be completed through Edit. Saving restarts activation with a new request UUID. Delete removes the address, bank row, and personal record in that order.

Failure between databases

Each database commits separately. The coordinator attempts to compensate for caught save or delete failures. A crash between writes or a failed repair can leave partial data that needs reconciliation by customer ID.

Kafka unavailable or messages redelivered

The scheduler retries events that remain in the outbox. A crash after Kafka acknowledges a send can cause a duplicate. The listener skips requests for completed, superseded, or deleted bank rows. Result consumers can deduplicate by request UUID.

Check the live flow locally

Start all three stores and the Docker Kafka broker, then run ./run.sh. Open the local dashboard, save a synthetic registration, and reload the grid. Look up the customer ID on both topics in Kafka UI and match the request UUID.
